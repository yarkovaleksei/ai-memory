# Журнал решений

Каждое решение — отдельная запись. Принятые записи не переписываются: если решение меняется, добавляется новая запись со ссылкой на старую, а у старой статус меняется на «заменено ADR-NNN».

Статусы: `предложено` — ждёт подтверждения владельца; `принято`; `отклонено`; `заменено ADR-NNN`.

## ADR-001. Работать поверх родной памяти агентов, без своего хранилища

**Статус:** принято (2026-11-10)

**Контекст.** Готовые решения (claude-mem, codemem, Basic Memory, mem0/OpenMemory) добавляют третий, отдельный слой памяти через MCP или хуки. Родную автопамять Claude и Codex они не видят и не правят.

**Решение.** ai-memory читает и пишет родные файлы памяти агентов. Свои данные системы — только индекс, кэш и бэкапы, их можно удалить и пересобрать.

**Последствия.** Агентов не нужно перенастраивать. Зато мы зависим от недокументированных форматов и должны переживать их изменения.

---

## ADR-002. В память Codex писать только ad-hoc-заметками

**Статус:** принято (2026-11-10)

**Контекст.** `memory_summary.md`, `MEMORY.md` и `rollout_summaries/` Codex пересобирает при консолидации, прямые правки будут потеряны. `extensions/ad_hoc/notes/` — штатный канал, который Codex считает авторитетным. Удалять заметки запрещено его же инструкцией.

**Решение.** Все изменения памяти Codex — новые или изменённые ad-hoc-заметки. Удаление факта — заметка «забыть». Сгенерированные файлы — только чтение.

**Последствия.** Изменения в Codex применяются не сразу, а после консолидации. Интерфейс должен показывать это состояние («ожидает консолидации»).

## ADR-003. Стек: TypeScript на Node 24, Hono, React + react-admin + MUI

**Статус:** отклонено (2026-11-10), заменено [ADR-006](#adr-006-стек-go--wails-v3-react-admin-yarn-4)

**Контекст.** Владелец — фронтенд-разработчик с опытом react-admin и MUI. Память — по сути CRUD над записями с фильтрами, это ровно задача react-admin. На машине есть Node 24 и npm; bun и cargo не установлены, pnpm через corepack сломан.

**Решение.**
- Монорепозиторий на npm workspaces: `packages/core`, `apps/server`, `apps/web`, позже `packages/mcp`.
- Сервер — Hono на `@hono/node-server`.
- Интерфейс — Vite + React + react-admin 5 + MUI, свой `dataProvider` поверх REST сервера.
- Редактор Markdown — CodeMirror 6, diff — `@codemirror/merge`.
- SQLite — `better-sqlite3` (FTS5 из коробки). Встроенный `node:sqlite` рассмотреть, когда стабилизируется.
- Тесты — Vitest; проверка типов — `tsc --noEmit`; линт — ESLint + Prettier.

**Последствия.** Один язык во всём проекте, адаптеры переиспользуются сервером и MCP-мостом.

**Контекст.** Tauri требует Rust, его на машине нет. Electron тяжёлый. Веб-интерфейс на localhost закрывает задачу «удобный GUI» сразу.

**Решение.** До фазы 5 — локальный сервер плюс страница в браузере. Вопрос упаковки (Tauri, Electron или PWA с автозапуском сервера) решается в фазе упаковки ([phases/06-packaging.md](phases/06-packaging.md)).

## ADR-005. LLM-операции через CLI агентов

**Статус:** принято (2026-11-10)

**Контекст.** Объединение дублей и переформулирование требуют LLM. У владельца есть подписки на Claude и Codex, отдельных API-ключей заводить не хочется.

**Решение.** Вызывать `claude -p` и `codex exec` в неинтерактивном режиме с промптом и данными через stdin. Ответ — черновик, который проходит обычный путь записи с diff.

**Последствия.** Нужно следить, чтобы такие вызовы не создавали память сами о себе (у Codex — сессия попадёт в конвейер генерации). Проверить в [фазе 3](phases/03-cross-agent.md).

## ADR-006. Стек: Go + Wails v3, react-admin, yarn 4

**Статус:** принято (2026-11-10). Заменяет ADR-003 и ADR-004.

**Контекст.** Владелец выбрал настоящее десктоп-окно с самого начала вместо вкладки браузера, react-admin для интерфейса и yarn 4 вместо npm. На машине уже стоят Go 1.26 и `wails3` v3.0.0, `wails3 doctor` проходит без замечаний (GTK 4 и WebKitGTK 6.0). На том же стеке у владельца уже есть другой проект: Wails v3, `internal/`, `frontend/` на yarn 4 с `nodeLinker: node-modules`, задачи в `Taskfile.yml`. ai-memory повторяет эти соглашения, чтобы не держать в голове два разных устройства проекта.

**Решение.**

| Слой | Выбор |
|---|---|
| Ядро | Go 1.26, один модуль в корне репозитория, пакеты в `internal/` |
| Окно | Wails v3: Go-сервисы вызываются из интерфейса через сгенерированные привязки, обновления — событиями Wails. HTTP-сервера нет |
| Интерфейс | `frontend/`: Vite + React + TypeScript (шаблон `wails3 init -t react`), react-admin 5 + MUI, свой `dataProvider` поверх привязок |
| Редактор и diff | CodeMirror 6 и `@codemirror/merge` |
| Пакеты фронтенда | yarn 4 (`packageManager: yarn@4.18.1`), `nodeLinker: node-modules`: Vite, ESLint и TypeScript в редакторе надёжнее работают с `node_modules`, чем с PnP |
| Задачи | `Taskfile.yml` (`wails3 task …`), задачи фронтенда вызывают `yarn`, а не `npm` |
| Индекс | SQLite через `modernc.org/sqlite` (чистый Go) с FTS5. Поддержку FTS5 и кириллицы проверить в фазе 0; запасной вариант — `mattn/go-sqlite3` с тегом `sqlite_fts5` |
| Frontmatter | `gopkg.in/yaml.v3` через `yaml.Node`, чтобы при записи сохранить порядок ключей и неизвестные поля |
| Наблюдение за файлами | `fsnotify`. На Linux он не рекурсивный: подписываться на каждый каталог памяти и на появление новых |
| Бэкапы | системный `git` через `os/exec` |
| MCP-мост | официальный `github.com/modelcontextprotocol/go-sdk`, отдельный бинарь `cmd/ai-memory-mcp` без зависимости от Wails и GTK |
| Тесты и проверки | `go test` (в том числе `-race`), `go vet`, `gofmt`, `staticcheck`; во фронтенде Vitest, `tsc --noEmit`, ESLint, Prettier |

**Последствия.**
- Два языка. Граница между ними — сервисы в `internal/app`, типы для TypeScript генерирует `wails3 generate bindings`.
- Ядро (`internal/` без `internal/app`) не зависит от Wails и тестируется без окна и без cgo.
- Сетевого порта в собранном приложении нет. В режиме `wails3 dev` фронтенд раздаёт dev-сервер Vite на localhost: проверить в фазе 0, что привязки при этом недоступны со сторонних страниц.
- Упаковка упрощается: `wails3 build` даёт один бинарь, [фаза 6](phases/06-packaging.md) сводится к ярлыку и установочному пакету.

## ADR-007. Открытый проект под лицензией MIT

**Статус:** принято (2026-11-10)

**Контекст.** Владелец решил сделать ai-memory открытым проектом. Задача «увидеть и привести в порядок память нескольких агентов» есть у любого, кто чередует Claude Code и Codex.

**Решение.**
- Лицензия MIT, файл `LICENSE` в корне.
- `README.md` на русском — основной, `README.en.md` — перевод для внешних читателей. План и документация разработчика остаются на русском.
- Работа идёт прямо в `main`, без веток и PR (см. раздел «Git» в `AGENTS.md`). Репозиторий на GitHub создаётся отдельно, когда владелец решит его опубликовать.

**Последствия.**
- Ничего, что работает только на машине владельца. Профили Claude ищутся в `~/.claude` и `CLAUDE_CONFIG_DIR`, дополнительные (вроде второго рабочего профиля) задаются в настройках приложения, а не зашиты в код. Корень Codex — `~/.codex` или `CODEX_HOME`.
- В коде, документации и фикстурах — никаких путей, имён проектов и данных с машины владельца.
- Появляется вопрос о macOS и Windows ([Q9](open-questions.md)).

## ADR-008. Интерфейс на русском через i18n с первого дня

**Статус:** принято (2026-11-10)

**Контекст.** Основной пользователь говорит по-русски, но проект открытый, и английский интерфейс понадобится. Если начать со строк прямо в коде, перевод потом превращается в переделку всех экранов.

**Решение.**
- Все строки интерфейса — через `i18nProvider` react-admin (`ra-i18n-polyglot`) и словари в `frontend/src/i18n/`. Первый и пока единственный словарь — `ru`.
- Для встроенных сообщений react-admin взять готовый русский пакет, если он совместим с react-admin 5 (проверить в фазе 0); иначе — свой словарь сообщений `ra.*`.
- Ядро на Go не отдаёт текст для человека: ошибки и предупреждения (`Warnings`) — это код и параметры, текст собирает фронтенд по словарю.
- Английский словарь добавляется, когда понадобится; переключение языка — в настройках приложения.

**Последствия.** Немного больше работы на каждом экране, зато английская версия — это только новый словарь.

## ADR-009. Linux, macOS и Windows с самого начала

**Статус:** принято (2026-11-10)

**Контекст.** Проект открытый ([ADR-007](#adr-007-открытый-проект-под-лицензией-mit)), Claude Code и Codex работают на всех трёх системах, Wails v3 собирает под все три. Владелец решил поддерживать все три с самого начала, а не переносить потом.

**Решение.**
- Код ядра переносим: пути только через `filepath`, `os.UserHomeDir`, `os.UserConfigDir`, `os.TempDir`; никаких `/` в путях и Linux-специфичных вызовов вне файлов с build-тегами.
- Каталоги ai-memory — по правилам каждой системы ([architecture.md](architecture.md#каталоги-ai-memory)).
- Тесты ядра проходят на всех трёх системах. Проверяет это CI-матрица GitHub Actions (`ubuntu`, `macos`, `windows`), которая начнёт работать, когда репозиторий будет опубликован. До этого локально проверяется только Linux, и это нужно честно отражать в отчётах.
- Сборка установочных пакетов под каждую систему — в [фазе 6](phases/06-packaging.md).

**Последствия.**
- Атомарная замена файла на Windows ведёт себя иначе: `os.Rename` поверх существующего файла не сработает, если файл открыт другим процессом (например, агентом). Writer должен распознавать эту ошибку и повторять попытку или сообщать о конфликте.
- Пути к памяти агентов на macOS и Windows и регистр имён файлов нужно проверить ([storage-formats.md](storage-formats.md)); в фикстурах — пути, собранные через `filepath`.
- Подпись и нотаризация для macOS и подпись для Windows — отдельный вопрос фазы 6; без них приложение запускается с предупреждением системы.

## ADR-010. Инструкции и навыки агентов — тоже в охвате

**Статус:** принято (2026-11-10)

**Контекст.** Владелец хочет видеть и переносить между агентами не только автопамять, но и инструкции (`CLAUDE.md`, `AGENTS.md`) и навыки (skills). Это другая природа данных: их пишет человек, а не агент, проектные инструкции лежат в git-репозиториях проектов, навыки часто подключены симлинками из общего каталога.

**Решение.**
- Отдельная [фаза 4](phases/04-instructions-skills.md) после переноса памяти между агентами: она переиспользует механизм переноса и записи, а MVP остаётся маленьким.
- Инструкции — глобальные файлы профилей агентов и проектные файлы в каталогах проектов, известных по памяти.
- Навыки — каталоги с `SKILL.md` в профилях агентов. Навыки плагинов и системные навыки Codex — только чтение. Навыки, выведенные Codex из памяти (`memories/skills`), — только чтение, как и прочие сгенерированные файлы Codex.
- Правки проектных инструкций — те же план, diff, снимок и бэкап, плюс предупреждение, что файл лежит в чужом git-репозитории и изменение появится в его `git status`.
- Если навык — симлинк в общий каталог, это показывается явно: правка затронет всех, кто на него ссылается. Перенос навыка в другого агента — по выбору копией или симлинком на тот же каталог.

**Последствия.**
- Модель записей расширяется новыми видами ([architecture.md](architecture.md#модель-данных)), MCP-мост сдвигается в фазу 5, упаковка — в фазу 6.
- Правило «не выходить за разрешённые корни» для навыков уточняется: цель симлинка навыка добавляется в разрешённые корни явно и видна пользователю.

## ADR-011. Markdown записей показывает react-markdown

**Статус:** принято (2026-11-10)

**Контекст.** Вся память агентов — Markdown: списки, таблицы GFM, код, ссылки `[[slug]]` у Claude и пути `rollout_summaries/…` у Codex. В react-admin и MUI отрисовщика Markdown нет, а писать свой разбор — источник ошибок.

**Решение.** `react-markdown` с `remark-gfm` (экосистема unified, без `dangerouslySetInnerHTML`: сырой HTML из файлов памяти не исполняется). Ссылки на другие записи до разбора превращаются в схему `aim-item:<id>`, её пропускает собственный `urlTransform`; внешние ссылки открываются в системном браузере через рантайм Wails, а не в окне приложения.

**Последствия.** +6 пакетов во фронтенде. Подсветка синтаксиса в блоках кода не нужна для MVP и не добавляется.

## ADR-012. Бэкапы через системный git, блокировка Codex через его же lock-файл

**Статус:** принято (2026-11-10)

**Контекст.** Фаза 2 требует снимка перед каждой записью и отката любой операции. Codex сам переписывает каталог памяти при консолидации, и писать заметку во время неё нельзя (Q2).

**Решение.**
- Репозиторий бэкапов — обычный git-репозиторий `backups/` в каталоге данных, управляется системным `git` через `os/exec`. Настройки git пользователя не действуют (`GIT_CONFIG_GLOBAL` на пустое устройство, без системного конфига, фиксированный автор, без подписи), концы строк не преобразуются (`* -text`). Перед записью — коммит снимка, после — коммит операции с метаданными в теле. Откат строится по родителю коммита операции.
- Встраиваемая реализация git (go-git) не берётся: лишняя тяжёлая зависимость, а `git` есть у всех, кто работает с этими агентами. Если его нет, запись недоступна с понятной ошибкой `backup.git-missing`, просмотр работает.
- Перед записью заметки ai-memory берёт тот же неблокирующий файловый lock (`memories_v2.lock`, `memories.lock`), что Codex 0.167 держит при консолидации, и держит его до конца записи; для 0.159 дополнительно проверяется строка задачи в `jobs`. На Windows lock берётся через `LockFileEx` из `golang.org/x/sys/windows` — пакет уже был в графе зависимостей (через fsnotify и Wails), теперь он прямой.

**Последствия.**
- Пока ai-memory пишет заметку, Codex пропускает консолидацию (`skipped_workspace_busy`) и повторит её в следующем ходе.
- Откат создания заметки Codex невозможен: он удалил бы файл заметки (ADR-002). Отменять такую заметку — новой заметкой «забыть». *Заменено [ADR-014](#adr-014-отмена-заметки-codex--переписать-её-текст-на-отмену): откат переписывает заметку на отмену.*

## ADR-013. Редактор и diff — CodeMirror 6 без обёртки для React

**Статус:** принято (2026-11-10)

**Контекст.** Фаза 2 правит Markdown фактов и заметок и перед записью показывает diff каждого файла. В react-admin и MUI нет ни редактора кода, ни просмотра различий; `<textarea>` не даёт подсветки Markdown, а самописный diff — источник ошибок.

**Решение.**
- Редактор — CodeMirror 6: `codemirror` (базовый набор расширений), `@codemirror/lang-markdown`, `@codemirror/state` и `@codemirror/view` (их импортируем напрямую, поэтому они в зависимостях явно).
- Diff — `@codemirror/merge`: две колонки «было / станет» для правки, одна колонка для созданного или удалённого файла. Неизменённые участки свёрнуты.
- Обёртку для React (`@uiw/react-codemirror` и подобные) не берём: нужен один небольшой компонент с `useEffect`, а обёртка тянет свои версии пакетов CodeMirror.
- Тема редактора строится из палитры MUI, отдельный пакет темы не нужен.

**Последствия.**
- +23 пакета во фронтенде: семейства `@codemirror` и `@lezer` (`lang-markdown` тянет разбор HTML, CSS и JavaScript для вставок) и три мелкие библиотеки самого CodeMirror.
- В jsdom CodeMirror не измеряет разметку, поэтому тесты Vitest подменяют компонент редактора обычным полем ввода; сам CodeMirror проверяется в окне при приёмке.

## ADR-014. Отмена заметки Codex — переписать её текст на отмену

**Статус:** принято (2026-11-10). Заменяет последствие ADR-012 «откат создания заметки Codex невозможен».

**Контекст.** Фаза 3 переносит факты между агентами и объединяет дубли, и такие операции часто создают заметки Codex: копию факта, «забыть» для перенесённой или объединённой записи. Критерий фазы — любая из них откатывается одной операцией. По ADR-012 откат создания заметки отклонялся: он удалил бы файл заметки, а это запрещено (ADR-002). Тогда перенос и объединение с участием Codex не откатывались бы вовсе.

**Решение.** Откат создания заметки не удаляет файл, а переписывает его: заголовок остаётся, текст заменяется сообщением, что пользователь отменил заметку и её прежнее содержимое не должно оставаться в памяти. Правку своей заметки Codex вливает при консолидации так же, как новую заметку (`extensions/ad_hoc/instructions.md`, [storage-formats.md](storage-formats.md#единственный-безопасный-канал-записи)). Остальные файлы операции откатываются как обычно, одним планом. Откат такого отката возвращает прежний текст заметки.

**Последствия.**
- Writer по-прежнему никогда не удаляет файлы заметок; меняется только план отката в сервисе истории.
- Если консолидация уже учла заметку, отмена подействует только после следующей консолидации; до неё Codex помнит факт. Интерфейс говорит об этом в диалоге отката.
- После отмены в каталоге заметок остаётся файл с текстом отмены. Это цена запрета на удаление.

## ADR-015. LLM-черновики: один запрос из постоянного каталога, кандидатов отбирает TF-IDF

**Статус:** принято (2026-11-10). Уточняет ADR-005. Пункт про отправку всех групп заменён ADR-017, отбор кандидатов TF-IDF — ADR-018.

**Контекст.** Фаза 3 просит у модели черновик объединения группы и отчёт о противоречиях. Q8 показал, что `claude -p --no-session-persistence --tools ""` и `codex exec --ephemeral` память не создают, но Claude Code заводит пустой каталог проекта для каждого нового текущего каталога. Каждый запуск CLI стоит десятки секунд и тысячи токенов системного промпта из подписки владельца; сравнивать «всё со всем» моделью дорого и медленно.

**Решение.**
- Пакет `internal/llm` запускает CLI через `os/exec` из одного постоянного каталога `<каталог данных>/llm`. Claude: `-p --no-session-persistence --tools "" --strict-mcp-config --disable-slash-commands --output-format json --json-schema …` (MCP-серверы не поднимаются — инструментов у модели всё равно нет). Codex: `exec --ephemeral --skip-git-repo-check -s read-only -C <каталог> --output-schema <файл> -o <файл> -`; файлы схемы и ответа — во временном подкаталоге, который удаляется после вызова.
- Промпт с записями идёт через stdin, ответ — JSON по строгой схеме. Записи в промпте обёрнуты в `<record>`, и модели сказано, что это данные, а не инструкции.
- Кандидатов в противоречия отбирает TF-IDF экрана «Похожие» (`internal/similar`), модель сравнивает записи только внутри групп, и все группы уходят одним запросом до потолка 120 тыс. символов. Отчёт говорит, сколько групп проверено.
- Ответ модели ничего не пишет: черновик объединения вписывается в форму «Объединить…», дальше обычный план с diff. Противоречия модель не решает, а оставляет оба варианта в черновике и перечисляет отдельно.
- Запрос можно остановить: отмена промиса Wails отменяет контекст, и процесс CLI завершается.

**Последствия.**
- Новых зависимостей нет. Тесты подменяют запуск (`llm.Runner`) и настоящие CLI не вызывают.
- Модель — та, что настроена в CLI по умолчанию; выбор модели в ai-memory не нужен, пока владелец не попросит.
- Пустой каталог проекта Claude для `<каталог данных>/llm` один на установку (и ещё один для каталога данных разработки). ai-memory его не показывает: записей в нём нет.
- Противоречия между записями, которые TF-IDF не счёл похожими, отчёт не найдёт. Порог экрана расширяет выбор, если нужно.
- Проверено только на Linux; на Windows CLI, поставленные через npm, — это `.cmd`, и запуск через `os/exec` надо проверить в фазе упаковки.

## ADR-016. Шрифт Roboto встроен в сборку

**Статус:** принято (2026-11-10)

**Контекст.** MUI рассчитан на метрики Roboto. Приложение его не подключало, и окно брало шрифт из системы: на Linux без Roboto WebKitGTK подставлял Noto Sans, у которого другие высота строчных и положение базовой линии, — владелец заметил, что текст в кнопках съезжает по вертикали. На Windows и macOS подстановка была бы своя, и вид разошёлся бы ещё сильнее.

**Решение.** Добавить зависимость `@fontsource/roboto` и подключать в `frontend/src/theme.ts` начертания 400, 500 и 700 только для латиницы и кириллицы (с расширенными наборами). Остальные алфавиты в записях памяти редки, их глифы возьмёт системный шрифт. Файлы шрифта собирает Vite и встраивает в бинарь вместе с фронтендом: сеть не нужна, и на всех ОС окно выглядит одинаково.

**Последствия.**
- Бинарь вырастает примерно на 400 КБ файлов шрифта; окно загружает только нужные по `unicode-range`.
- Пакет — только CSS и файлы шрифта под лицензией OFL, без кода.

## ADR-017. Модели уходят только отмеченные записи

**Статус:** принято (2026-11-10). Заменяет пункт ADR-015 «все группы уходят одним запросом». Группы похожих убраны ADR-018; принцип «модели уходят только отмеченные записи» остаётся.

**Контекст.** Проверка противоречий отправляла модели все группы экрана «Похожие». На реальной памяти владельца TF-IDF находит 15 групп, и одна большая группа длинных записей уже не помещалась в предел запроса — проверка падала с ошибкой, хотя владелец отметил одну небольшую группу. Отметки в карточках при этом на запрос не влияли, и было неясно, что именно уйдёт модели.

**Решение.** Отметки записей подняты на уровень экрана и по умолчанию пусты. В проверку противоречий уходят только отмеченные записи, по группам; группы, где отмечено меньше двух, пропускаются. Экран показывает, сколько записей и групп уйдёт, кнопки проверки выключены, пока ничего не отмечено. Ошибка «не помещается» называет фактический размер запроса. Поиск групп по-прежнему без LLM.

**Последствия.** Чтобы проверить всё, нужно отметить всё — это осознанное действие, а объём запроса виден до отправки. Объединение и сравнение работают с теми же отметками.

## ADR-018. Без поиска похожих по совпадению слов: объединение и противоречия — для отмеченных в списке

**Статус:** принято (2026-11-10). Заменяет отбор кандидатов TF-IDF из ADR-015 и группы из ADR-017.

**Контекст.** Экран «Похожие» искал кандидатов в дубли по совпадению буквенных триграмм (`internal/similar`). На реальной памяти владельца он связывал записи, у которых просто общие технические слова, и не связывал одинаковое по смыслу на разных языках («Отвечать по-русски» и «Respond in Russian»). Владелец решил, что такой поиск не несёт пользы, а только внушает, что найдены настоящие совпадения.

**Решение.** Убрать экран «Похожие», пакет `internal/similar` и метод `LibraryService.Similar`. Объединение и проверка противоречий остаются, но работают с записями, которые пользователь сам отметил в списке «Записи» (поиск и фильтры помогают их найти): групповые действия «Объединить» (тот же диалог с черновиком от модели, одна операция и один откат) и «Найти противоречия» (модели уходят только отмеченные записи). Отмечать можно факты Claude и записи Codex, которые объединение умеет убрать заметкой «Забыть».

**Последствия.**
- Дубли ищет человек, ai-memory их не угадывает. Поиск дублей по смыслу через модель возможен позже, но это запрос на всю память, дорогой и с пределом объёма; без запроса владельца не делаем.
- Критерий фазы 3 про «Похожие» заменён: объединение отмеченных записей работает одной операцией и откатывается одной операцией.

## ADR-019. Как читаются инструкции и навыки

**Статус:** принято (2026-11-10). Уточняет [ADR-010](#adr-010-инструкции-и-навыки-агентов--тоже-в-охвате) по итогам исследования фазы 4 ([storage-formats.md](storage-formats.md#инструкции-и-навыки)). Источник путей проектов дополнен в [ADR-025](#adr-025-пути-проектов-для-инструкций--и-из-каталогов-проектов-claude-без-памяти).

**Контекст.** Инструкции и навыки лежат не в каталогах памяти: в корне профиля Claude и `CODEX_HOME`, в `~/.agents/skills`, в каталогах проектов. Проектные файлы можно найти, только когда пути проектов уже известны из памяти. Корни профиля и `CODEX_HOME` агенты постоянно меняют сами: история, логи, сессии.

**Решение.**
- Два новых вида записей: `instructions` (один файл инструкций) и `skill` (каталог с `SKILL.md`). Запись — файл целиком; нарезка по заголовкам нужна только для переноса правила и делается в момент переноса.
- Что читается:
  - инструкции Claude — `<профиль>/CLAUDE.md`, `<профиль>/rules/**/*.md`, в проекте `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, `.claude/rules/**/*.md`;
  - инструкции Codex — `AGENTS.override.md` и `AGENTS.md` в `CODEX_HOME` и в каталоге проекта;
  - навыки Claude — `<профиль>/skills`, синхронизированные с аккаунтом `<профиль>/skills/synced` (только чтение), проектные `.claude/skills`;
  - навыки Codex — `~/.agents/skills` и `CODEX_HOME/skills`, системные `CODEX_HOME/skills/.system` (только чтение), проектные `.agents/skills` и `.codex/skills`, навыки из памяти `memories*/skills` (только чтение, их читает адаптер памяти Codex).
- Чего не читаем в фазе 4: `CLAUDE.md` и `AGENTS.md` во вложенных каталогах проекта (их пришлось бы искать обходом всего репозитория), системный managed-файл Claude и `/etc/codex/skills`, навыки плагинов обоих агентов, старые команды `commands/*.md`. Если понадобятся — отдельной задачей.
- `~/.agents/skills` относится к Codex: Codex читает его сам, а Claude видит эти навыки только через симлинки в профиле.
- Проектные файлы читаются для проектов с восстановленным путём: библиотека сначала читает память, потом по найденным путям — проектные файлы. Записи временных проектов скрыты из списка, как и их память.
- Навык помечается общим, если на один и тот же каталог (после раскрытия симлинков) указывают несколько записей — разных профилей или разных агентов. Такие записи ссылаются друг на друга.
- Файл проекта внутри git-репозитория помечается: в записи хранится корень репозитория.
- Новые хранилища (`Source`) с признаком `files`: файлы каждого профиля Claude, `CODEX_HOME`, `~/.agents` и проектные файлы каждого агента. Признак отделяет их от хранилищ памяти там, где речь именно о памяти (например, куда можно записать факт).
- Наблюдение за корнем профиля, `CODEX_HOME` и каталогами проектов — только по именам файлов инструкций: изменения истории, логов и прочих файлов агента индекс не пересобирают.

**Последствия.**
- Запись инструкций и навыков (план, diff, бэкап, предупреждение о чужом git-репозитории и об общем навыке) — следующий шаг фазы; пока эти записи только читаются, а действия памяти (перенос факта, объединение, удаление) к ним не применяются.
- Разрешённые корни writer'а расширятся каталогами проектов и `~/.agents`, когда появится запись.

## ADR-020. Как пишутся инструкции и навыки

**Статус:** принято (2026-11-10). Уточняет [ADR-010](#adr-010-инструкции-и-навыки-агентов--тоже-в-охвате) и [ADR-019](#adr-019-как-читаются-инструкции-и-навыки). Пункт об удалении файлов Codex уточнён в [ADR-021](#adr-021-перенос-правила--раздел-по-заголовку-вставкой-в-другой-файл-инструкций).

**Контекст.** Инструкции и навыки лежат вне каталогов памяти: в каталогах проектов (чаще всего под git), в `~/.agents`, а каталог навыка бывает симлинком в общее место, на которое ссылаются несколько профилей и агентов. Writer пускал запись только в профили Claude и `CODEX_HOME`, а защита Codex — только в ad-hoc-заметки.

**Решение.**
- Правка — исходник файла целиком (`CLAUDE.md`, `AGENTS.md`, правило, `SKILL.md`) через `PlansService.UpdateSource`: тот же план, diff, снимок в бэкап и откат, что у памяти. Остальные файлы каталога навыка не правятся.
- Разрешённые корни writer'а — ещё `~/.agents`, каталоги проектов из индекса и цели симлинков навыков из индекса. Их собирает Go на каждое применение, интерфейс путей не передаёт; откат получает те же корни.
- Защита Codex пропускает в `CODEX_HOME` также `AGENTS.md`, `AGENTS.override.md` и файлы пользовательских навыков в `skills/<навык>/`. Это не память: блокировка консолидации для них не берётся. Системные навыки `skills/.system` и сгенерированные файлы памяти по-прежнему только для чтения. Удалять инструкции и навыки Codex ai-memory не умеет и не даёт.
- У плана есть предупреждения кодом с параметрами. «Файл в git-репозитории проекта» — показать, что правка появится в его `git status`; ai-memory в чужой репозиторий не коммитит. «Общий навык» — каталог подключён симлинком или в нескольких местах, правка затронет всех; записать можно только после отдельного подтверждения в окне плана.

**Последствия.**
- Перенос правила и навыка между агентами (следующие задачи фазы 4) строится из тех же планов и предупреждений.
- Подтверждение общего навыка — в интерфейсе: writer его не проверяет, как и прочие подтверждения записи.

## ADR-021. Перенос правила — раздел по заголовку вставкой в другой файл инструкций

**Статус:** принято (2026-11-10). Уточняет [ADR-020](#adr-020-как-пишутся-инструкции-и-навыки).

**Контекст.** Правило из `CLAUDE.md` нужно и Codex, и наоборот, но переносить файл целиком нельзя: в нём правила одного агента, импорты `@путь`, которых Codex не понимает, и чужие разделы. Отдельной записью в индексе правило не выделить: файлы инструкций читаются целиком (ADR-019), и нарезка на записи сломала бы правку исходника. Файла второго агента в проекте часто нет вовсе. Claude Code сам читает `AGENTS.md`, только пока рядом нет `CLAUDE.md` ([storage-formats.md](storage-formats.md#инструкции-и-навыки)).

**Решение.**
- Правило — раздел по ATX-заголовку вместе с подразделами. Текст до первого заголовка — тоже раздел. Заголовки в блоках кода и frontmatter правила не считаются. Разделы считаются при открытии диалога с диска, а не хранятся в индексе. Интерфейс возвращает номер раздела вместе с хэшем файла: изменился файл — план не строится.
- Перенос — вставка раздела в конец другого файла инструкций того же проекта (или глобального) либо в конец выбранного раздела цели. Копия не меняет исходный файл, перенос убирает из него раздел той же операцией. Откат возвращает оба файла.
- Цели считает Go: файлы инструкций проекта по ID записи и отсутствующие главные файлы агентов по ключу `new:<хранилище>`. Это `AGENTS.md` в каталоге проекта или `CODEX_HOME`, `CLAUDE.md` в каталоге проекта или профиле. Путь нового файла интерфейс не передаёт. Новый `CLAUDE.md` рядом с `AGENTS.md` начинается с `@AGENTS.md`: иначе Claude Code перестал бы читать правила `AGENTS.md`.
- Импорты `@путь` не переписываются и не раскрываются. Раздел с импортами, который идёт в Codex, получает предупреждение в плане. Ещё предупреждения: цель уже импортирует исходный файл, в цели есть раздел с тем же заголовком, `AGENTS.md` затенён `AGENTS.override.md`, правило-цель условное (`paths`), инструкции проекта Codex больше 32 КиБ. Плюс предупреждения ADR-020 о git-репозитории проекта.
- Файл инструкций или навыка Codex удаляет только откат: он возвращает состояние из снимка, то есть убирает файл, созданный самой ai-memory. Любое другое удаление по-прежнему запрещено защитой Codex. Заметки Codex не удаляются и откатом (ADR-002).

**Последствия.**
- Переносится и правило между файлами одного агента (из `CLAUDE.md` в `.claude/rules/…`): в целях файлы другого агента идут первыми, но и свои не скрыты.
- Уровень заголовка при вставке не меняется: предпросмотр плана показывает, как раздел ляжет в цель.
- Правило, разбросанное по нескольким разделам или записанное без заголовка в середине чужого раздела, переносится правкой исходника, а не этим диалогом.

## ADR-022. Приём «AGENTS.md — основной» — блоки CLAUDE.md переносятся, в CLAUDE.md остаётся импорт

**Статус:** принято (2026-11-10). Опирается на [ADR-021](#adr-021-перенос-правила--раздел-по-заголовку-вставкой-в-другой-файл-инструкций).

**Контекст.** Самый надёжный способ дать обоим агентам одни правила проекта — держать их в `AGENTS.md`, а в `CLAUDE.md` импортировать его строкой `@AGENTS.md` ([storage-formats.md](storage-formats.md#инструкции-и-навыки)). Так устроен и этот репозиторий. Но какие правила общие, а какие только для Claude, по тексту не определить.

**Решение.**
- Предложение показывается в предпросмотре главного файла инструкций проекта, если приём ещё не сделан. Варианты: есть оба файла, а `CLAUDE.md` не импортирует `AGENTS.md`; есть только `CLAUDE.md`; есть только `AGENTS.md`. Главный файл Claude — `CLAUDE.md` в корне проекта, иначе `.claude/CLAUDE.md`; импорт тогда `@../AGENTS.md`.
- `CLAUDE.md` режется на блоки, которые идут подряд и покрывают файл: текст до первого заголовка и разделы верхнего уровня. Если весь файл — один раздел `# Заголовок`, блоками становятся его вступление и подразделы. Что уходит в `AGENTS.md`, выбирает пользователь. По умолчанию отмечено похожее на общее: не вступление, без импортов `@` и без «Claude» в заголовке.
- Отмеченные блоки уходят в конец `AGENTS.md` или становятся новым `AGENTS.md`. Пустой новый `AGENTS.md` не создаётся. В `CLAUDE.md` остаётся остальное и строка импорта: после вступления, если оно осталось, иначе в начале. Нет `CLAUDE.md` — он создаётся из одной строки импорта. Всё одним планом с diff, откат возвращает оба файла.
- Предупреждения плана: импорты в переносимых блоках, `AGENTS.override.md` рядом, git-репозиторий проекта.

**Последствия.**
- Эвристика выбора по умолчанию — подсказка, а не решение: пользователь видит каждый блок и итоговый diff.
- Блоки дробнее верхнего уровня (подраздел внутри общего раздела) переносятся диалогом «Перенести правило» (ADR-021).

## ADR-023. Навык ставится в другого агента копией или симлинком через writer

**Статус:** принято (2026-11-10). Уточняет [ADR-020](#adr-020-как-пишутся-инструкции-и-навыки).

**Контекст.** Навык — каталог с `SKILL.md` и, бывает, скриптами. Оба агента понимают один формат, но читают разные поля frontmatter и ищут навыки в разных местах ([storage-formats.md](storage-formats.md#инструкции-и-навыки)). Общий навык удобнее держать симлинком, но writer умел только файлы с текстом и отказывал на любом симлинке.

**Решение.**
- Цели считает Go по уровню навыка. Глобальный навык Claude ставится в `~/.agents/skills/<имя>` (рекомендуется: основной путь Codex) или в `CODEX_HOME/skills/<имя>` (устаревший путь). Глобальный навык Codex — в `<профиль>/skills/<имя>`. Проектные — в `.agents/skills` или `.claude/skills` того же проекта. Занятое место (симлинк, файл или каталог с файлами) не предлагается и не перезаписывается.
- Копия переносит все обычные файлы каталога байт в байт и сохраняет право на исполнение. Скрытые каталоги (`.git`) и симлинки внутри навыка не копируются, о симлинках план предупреждает. Предел — 200 файлов и 4 МиБ: больше — это уже не навык, его ставят симлинком.
- Симлинк ведёт на настоящий каталог навыка (симлинки раскрыты). Writer умеет создавать и удалять симлинки (`Change.Link`, `Change.BeforeLink`), но никогда не пишет через них. Место симлинка проверяется по его каталогу, цель может лежать вне корней: туда ничего не пишется. В метаданных операции хранится, где были симлинки и исполняемые файлы, — откат и откат отката восстанавливают их. Защита Codex пропускает симлинк в `CODEX_HOME/skills/<имя>`.
- `SKILL.md` не переписывается. План перечисляет поля frontmatter, которые второй агент молча проигнорирует. Для Codex он ещё предупреждает, если нет `description` (навык не загрузится) или `name` длиннее 64 символов. Для Claude — что `agents/openai.yaml` он не читает. Для симлинка — что навык станет общим.

**Последствия.**
- Откат копии удаляет файлы, но оставляет пустые каталоги: writer удаляет только то, что записал. Пустой каталог не считается занятым местом, и навык можно поставить туда снова.
- На Windows симлинк требует прав или режима разработчика. Без них запись отказывает с понятной ошибкой, а копия работает всегда.
- Правка навыка, поставленного симлинком, идёт по правилам общего навыка ADR-020: с отдельным подтверждением.

## ADR-024. Инструкции отмечаются в списке только для проверки противоречий и дублей с памятью

**Статус:** принято (2026-11-10). Уточняет [ADR-018](#adr-018-без-поиска-похожих-по-совпадению-слов-объединение-и-противоречия--для-отмеченных-в-списке) и [ADR-019](#adr-019-как-читаются-инструкции-и-навыки).

**Контекст.** Частый беспорядок — правило записано и в `CLAUDE.md`, и фактом в автопамяти, или они расходятся. Дубли и противоречия ищет модель среди отмеченных записей (ADR-018), а инструкции отметить было нельзя: объединение и удаление их не умеют убрать.

**Решение.**
- Файлы инструкций отмечаются в списке наравне с памятью. Навыки — нет.
- С отмеченными инструкциями работает только «Найти противоречия». «Объединить» неактивна, и Go отказывает в черновике объединения (`plan.not-memory`). «Удалить» по-прежнему только для фактов Claude.
- В промпте инструкции помечены `kind="instructions"` и именем файла. Модель кроме противоречий ищет дубли: запись памяти, которая лишь повторяет правило из инструкций. В ответе у находки есть вид: `contradiction` или `duplicate`.
- У дубля в диалоге есть кнопка «Удалить факт» для лишнего факта Claude. Пару с инструкциями нельзя объединить: инструкции правятся своим редактором или переносом правила.

**Последствия.**
- В модель уходят только отмеченные файлы, как и раньше (ADR-017). Большой `CLAUDE.md` может упереться в предел запроса, тогда отмечают меньше.
- Лишняя запись Codex убирается заметкой «Забыть» из её карточки. Отдельной кнопки в находке у неё нет.

## ADR-025. Пути проектов для инструкций — и из каталогов проектов Claude без памяти

**Статус:** принято (2026-11-11). Уточняет [ADR-019](#adr-019-как-читаются-инструкции-и-навыки).

**Контекст.** По ADR-019 проектные инструкции и навыки ищутся по путям проектов, известным из памяти. На приёмке фазы 4 выяснилось: у большинства проектов Claude нет ни одного факта автопамяти (у владельца — 44 из 58). Сессии в них есть, а `CLAUDE.md` и `AGENTS.md` не видны, и проекта нет в списке.

**Решение.**
- Пути проектов для инструкций и навыков — это пути из памяти плюс пути всех каталогов `<профиль>/projects/<имя>`, в том числе без `memory/`. Путь восстанавливается так же, как для памяти: только поле `cwd` из начала файлов сессий, иначе подбором по диску. Нераспознанные имена пропускаются.
- Временные пути не отбрасываются, как и в памяти. Каталоги, которых уже нет, отсеивает адаптер инструкций.
- Проект попадает в список, только если у него нашлась хотя бы одна запись: память, инструкции или навык.

**Последствия.**
- В списке появляются проекты, где у Claude только инструкции: для них работают перенос правила, приём «`AGENTS.md` — основной» и установка навыков.
- Наблюдение ставится и на корни этих проектов, но только по именам файлов инструкций (ADR-019).
- Проекты, где был только Codex, по-прежнему видны, только если о них есть память Codex: файлы его сессий ai-memory не читает.

## ADR-026. MCP-мост: свой индекс в памяти, текущий проект, память другого агента

**Статус:** принято (2026-11-11).

**Контекст.** Фаза 5 даёт агенту инструменты MCP для поиска в памяти другого агента. Мост запускает сам агент: Claude Code или Codex поднимает stdio-сервер в начале сессии, без окна ai-memory. В фазе 5 предлагалось открыть общий с окном `index.db` в режиме WAL. Однако `index.Open` пересоздаёт таблицы, если версия схемы не совпала, и мост другой версии стёр бы индекс окна. А без окна общий индекс устаревает. Корни клиента (`roots/list`) в протоколе MCP 2026-07-28 устарели (SEP-2577), и сервер больше не может запросить их посреди вызова инструмента.

**Решение.**
- `cmd/ai-memory-mcp` — отдельный бинарь на `github.com/modelcontextprotocol/go-sdk` (уже есть в стеке [ADR-006](#adr-006-стек-go--wails-v3-react-admin-yarn-4)). Инструменты живут в ядре, в `internal/bridge`, без Wails.
- Индекс у моста свой, в памяти процесса (`library.NewInMemory`). Память перечитывается перед вызовом, если с прошлого раза прошло больше 10 секунд (`-refresh`). Каталоги данных и настроек ai-memory мост не создаёт и не меняет. `config.toml` он только читает, чтобы корни памяти совпадали с окном.
- Инструменты только на чтение и с `readOnlyHint`: `list_projects`, `search_memory(query?, project?, agent?, kind?, limit?)`, `get_memory(id)`. Поиск отдаёт id, заголовок, описание (до 300 символов), сниппет и вид записи: `memory`, `instructions` или `skill`, плюс формат хранения. Тело отдаёт только `get_memory`, не больше 64 КиБ.
- Текущий проект берётся из флага `-project`, а без него — из рабочего каталога процесса: агенты запускают сервер в каталоге сессии. Это проект, путь которого совпадает с каталогом или содержит его; из вложенных берётся самый глубокий. Корни клиента не спрашиваются.
- Видимость задаётся флагами сервера, а не аргументами: агент не может расширить её сам. По умолчанию виден только текущий проект. `-global` добавляет глобальную память, `-all-projects` — все проекты и `project: "all"`. `get_memory` не отдаёт запись невидимого проекта, даже по известному id.
- Поиск по умолчанию идёт по записям другого агента: свои агент и так видит. Агент берётся из флага `-agent`, иначе угадывается по имени клиента из `initialize` (`codex…`, `claude…`). Если агент неизвестен, поиск идёт по обоим. Аргумент `agent: "all"` возвращает и свои записи.
- Описания инструментов и подсказка `instructions` написаны по-английски: их читает модель, а не человек, и i18n интерфейса ([ADR-008](#adr-008-интерфейс-на-русском-через-i18n-с-первого-дня)) к ним не относится. Ошибки инструментов — тоже по-английски, с подсказкой, какой флаг нужен.
- `propose_memory` отложен. Критерий фазы — «ни один инструмент MCP не меняет файлы на диске», а черновик пришлось бы писать в каталог данных, и окну нужен приёмник таких черновиков. Это отдельное решение, если инструмент понадобится.

**Последствия.**
- Мост и окно не делят файлов и не мешают друг другу. Цена — пересборка индекса при старте моста и не чаще раза в 10 секунд; на фикстурах это доли секунды, на памяти владельца проверить на приёмке.
- Каталог сессии у Claude Code и Codex и имена их клиентов в `initialize` проверяются на приёмке. Если угадывание не сработает, флаги `-agent` и `-project` в инструкции подключения его заменяют.
- Подключение без записи в `~/.claude*` и `~/.codex` для разработки и приёмки: `claude --mcp-config`, `codex -c mcp_servers…` (`wails3 task mcp:dev`).

## ADR-027. Упаковка без подписи: deb, rpm, Arch, dmg и NSIS с MCP-мостом

**Статус:** принято (2026-11-11).

**Контекст.** Фаза 6 ставит ai-memory как обычное приложение на трёх системах ([ADR-009](#adr-009-linux-macos-и-windows-с-самого-начала)). Владелец решил: подписи и нотаризации не будет — ни аккаунта Apple Developer, ни сертификата для Windows. MCP-мост ([ADR-026](#adr-026-mcp-мост-свой-индекс-в-памяти-текущий-проект-память-другого-агента)) агенты запускают по пути из своих настроек, поэтому путь к нему должен быть известен заранее. Шаблоны сборки Wails в `build/` дают deb, rpm, пакет Arch, AppImage, `.app` с `.dmg` и установщик NSIS.

**Решение.**
- Linux: deb (Ubuntu 24.04+, Debian 13+), rpm (Fedora) и пакет Arch через nfpm (`wails3 tool package`), только amd64. Окно и мост — в `/usr/bin`. AppImage не собираем: WebKitGTK 6.0 держит вспомогательные процессы по путям системы и плохо переносится внутрь образа, а GTK 4 и WebKitGTK 6.0 и так ставятся зависимостями пакетов.
- macOS: универсальный `.app` (arm64 + amd64) в `.dmg`, подпись ad-hoc (`codesign --sign -`), без нотаризации. Мост — внутри приложения: `ai-memory.app/Contents/MacOS/ai-memory-mcp`.
- Windows: установщик NSIS для текущего пользователя, без прав администратора, в `%LOCALAPPDATA%\Programs\ai-memory`. Мост — рядом с окном: `ai-memory-mcp.exe`. WebView2 установщик докачивает, если его нет. Шаблон Wails по умолчанию ставил в Program Files с запросом UAC, но неподписанный установщик с правами администратора пугает сильнее, а данные ai-memory всё равно пользовательские.
- Мост — консольное приложение на чистом Go (`CGO_ENABLED=0`, без `-H windowsgui`), собирается под любую систему с любой машины.
- Версия — из тега `vX.Y.Z` (`git describe`), вшивается в оба бинаря через `-X main.version`. В Info.plist и установщик NSIS идёт числовая часть `X.Y.Z`, другую они не принимают.
- Релиз собирает GitHub Actions по тегу (`.github/workflows/release.yml`): каждая система — на своём раннере, пакеты и `SHA256SUMS` прикладываются к релизу. Подписанных артефактов нет. README объясняет, как открыть приложение: «Всё равно открыть» или `xattr -dr com.apple.quarantine` на macOS, «Подробнее» → «Выполнить в любом случае» в SmartScreen на Windows.
- Пакеты не трогают каталоги данных и настроек пользователя ни при обновлении, ни при удалении.

**Последствия.**
- При первом запуске пользователь macOS и Windows видит предупреждение системы. Обходить его ai-memory не пытается.
- Пакеты для macOS и Windows собираются в CI, но запустить их негде, пока у проекта нет машин или раннеров с этими системами. Установщик Windows кросс-собирается и на Linux (`makensis`); универсальный `.app` и `.dmg` — только на macOS.
- Arm64 для Linux и Windows не собирается. Добавить его — строка в матрице CI и `ARCH=arm64`, если появится спрос.

## ADR-028. deb ставит профиль AppArmor с правилом userns

**Статус:** принято (2026-11-11). Уточняет [ADR-027](#adr-027-упаковка-без-подписи-deb-rpm-arch-dmg-и-nsis-с-mcp-мостом).

**Контекст.** На приёмке фазы 6 окно из deb не открывалось из меню Ubuntu: процесс падал при старте с SIGTRAP в `webkit_web_view_evaluate_javascript`. WebKitGTK запускает свою песочницу через bubblewrap в user namespace. В Ubuntu 23.10+ включён `kernel.apparmor_restrict_unprivileged_userns=1`, и программе без своего профиля AppArmor создать его не даёт: в журнале ядра — `apparmor="DENIED" … comm="bwrap"`. Из терминала окно запускалось, потому что наследовало профиль терминала с правом на userns, и разработка этого не замечала.

**Решение.**
- deb ставит `/etc/apparmor.d/ai-memory` — профиль для `/usr/bin/ai-memory` с `flags=(unconfined)` и единственным правилом `userns`, как у Chrome и VS Code в Ubuntu. Права приложения он не сужает и не расширяет ничем, кроме user namespace.
- `postinstall` загружает профиль через `apparmor_parser -r`, если AppArmor включён, `preremove` выгружает его при удалении. Место для своих правил — `/etc/apparmor.d/local/ai-memory`.
- Песочницу WebKit не отключаем (`WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS`): она изолирует веб-содержимое окна, и отключение было бы шагом назад.
- rpm и пакет Arch профиля не несут: в Fedora SELinux, в Arch AppArmor по умолчанию выключен.

**Последствия.**
- Пакет пишет в `/etc/apparmor.d`. Это обычное место для профилей пакетов Ubuntu.
- MCP-мосту профиль не нужен: у него нет WebKit и песочницы.
- Проверять окно из пакета нужно запуском из меню, а не из терминала.

## ADR-029. Linux собирается локально, macOS и Windows — в CI

**Статус:** принято (2026-11-11), уточнено [ADR-030](#adr-030-релиз-выкладывается-черновиком-и-публикуется-после-сверки-по-api). Уточняет [ADR-027](#adr-027-упаковка-без-подписи-deb-rpm-arch-dmg-и-nsis-с-mcp-мостом).

**Контекст.** По ADR-027 все пакеты собирал CI. Владелец собирает свои проекты на Wails локально. Проверить пакеты он может только на Linux: Mac у него нет, а в виртуальной машине с Windows нет агентов. Пакеты Linux и установщик Windows собираются на его машине. Рабочий пакет для macOS с Linux не собрать: образ `wails-cross` даёт `.zip` без `.dmg` и без подписи ad-hoc, а без неё arm64-бинарь на Apple Silicon не запускается.

**Решение.**
- Linux собирает и выкладывает владелец: `wails3 task release` кладёт deb, rpm и пакет Arch в `bin/release/<версия>/` с `SHA256SUMS-linux.txt`. Затем `wails3 task release:publish` прикладывает их к релизу GitHub через `gh`. Версия — только чистый тег `vX.Y.Z` на текущем коммите, иначе задача отказывает.
- macOS и Windows собирает GitHub Actions по тегу (`release.yml`) на своих раннерах. Пакеты прикладываются к тому же релизу, у каждой системы свой `SHA256SUMS-<система>.txt`: общий файл двум сборщикам пришлось бы делить.
- Релиз создаёт тот, кто первый: CI или `release:publish`. Второй только докладывает файлы (`gh release upload --clobber`).

**Последствия.**
- Порядок выпуска: тег, `git push` тега, `wails3 task release`, `wails3 task release:publish`. Пакеты macOS и Windows появляются в релизе, когда CI доработает.
- То, что владелец выкладывает для Linux, — ровно то, что он у себя поставил и проверил.
- Пакеты macOS и Windows по-прежнему никем не запускались. Проверки на этих системах ждут пользователя с Mac или Windows.

## ADR-030. Релиз выкладывается черновиком и публикуется после сверки по API

**Статус:** принято (2026-11-11). Уточняет [ADR-029](#adr-029-linux-собирается-локально-macos-и-windows--в-ci).

**Контекст.** По ADR-029 релиз создавался сразу опубликованным, а файлы загружались с `--clobber`. Тогда пользователь мог увидеть релиз без пакетов macOS и Windows, пока CI не доработал, а повторный запуск молча перезаписывал уже выложенный файл. В проектах владельца на том же стеке (Forktopus, SongFrame) выпуск устроен иначе: черновик, сверка каждого вложения по digest из API GitHub, затем публикация.

**Решение.**
- CI и `wails3 task release:publish` создают релиз черновиком; кто первый, тот и создаёт, второй только докладывает файлы. Загрузка без `--clobber`.
- `wails3 task release:verify` (`scripts/release-verify.sh`) сверяет все восемь ожидаемых файлов по метаданным API: `state=uploaded` и digest SHA-256. Пакеты Linux сверяются с локальными файлами, пакеты macOS и Windows — с их `SHA256SUMS-<система>.txt` из того же релиза. Сами пакеты обратно не скачиваются.
- `wails3 task release:promote` публикует черновик как latest только после полной сверки и сверяет ещё раз.
- Проверки пакета Linux: `smoke:mcp` (мост по stdio на копии фикстур) и `smoke:desktop` (окно через пользовательский systemd, как из меню, ADR-028).
- Порядок выпуска и границы поручений описаны в навыках `ai-memory-build` и `ai-memory-release` (`.agents/skills/`, для Claude Code — симлинки в `.claude/skills/`).

**Последствия.**
- Опубликованный выпуск неизменен: тег не переносится, файлы не перезаписываются, ошибку исправляет следующая версия.
- Публикация — отдельный осознанный шаг, а не побочный эффект push тега.

## ADR-031. Обновление из приложения: проверка по кнопке, сверка и установка средствами системы

**Статус:** принято (2026-11-11).

**Контекст.** По ADR-027 новая версия ставится новым пакетом поверх старой, и пользователь сам узнаёт о выпуске на странице релизов. В проектах владельца на том же стеке (SongFrame, Forktopus) приложение само находит выпуск на GitHub, скачивает и сверяет пакет. SongFrame ещё и ставит его сам, но это нужно в основном для AppImage, которого у ai-memory нет (ADR-027). deb, rpm и пакет Arch без прав root не поставить, `.app` из `.dmg` переносит пользователь. Встроенный механизм обновления Wails не подходит по тем же причинам, что записаны у Forktopus: ответ 404 он принимает за «версия актуальна», JSON читает без ограничения размера, а контрольная сумма у него необязательна.

**Решение.**
- Пакет `internal/updates` в ядре, без Wails и без новых зависимостей: `net/http` и `crypto/sha256`.
- Проверка — только по кнопке в настройках. Автопроверки при запуске и по таймеру нет: без действия пользователя приложение в сеть не ходит.
- Источник — `https://api.github.com/repos/yarkovaleksei/ai-memory/releases/latest`. Учитывается только тег `vX.Y.Z`; черновики и пререлизы GitHub в latest не отдаёт, а если отдаст — они пропускаются. Ответ API читается не больше 1 МиБ. Запросы и перенаправления ходят только на `api.github.com`, `github.com`, `objects.githubusercontent.com` и `release-assets.githubusercontent.com`, перенаправлений не больше пяти.
- Формат пакета известен из сборки, а не угадывается по окружению. В бинарь для `.dmg` и установщика NSIS он вшит (`-X main.packageFormat=dmg|nsis`). deb, rpm и пакет Arch ставят один и тот же бинарь, поэтому каждый кладёт метку `/usr/share/ai-memory/package-format`, и читает её только бинарь, запущенный из `/usr/bin/ai-memory`. Без формата (`wails3 task dev`, сборка из исходников) проверка не ходит в сеть и сообщает, что эта сборка обновляется вручную.
- Имя пакета для формата — то же, под которым он лежит в релизе (ADR-029, ADR-030). SHA-256 скачанного файла сверяется с `SHA256SUMS-<система>.txt` того же релиза, а если у вложения есть `digest` из API — то и с ним; размер — с размером вложения. Несовпадение — ошибка, файл удаляется. Скачанный пакет лежит в `updates/<версия>/` в каталоге данных ai-memory, рядом с индексом и бэкапами, и перед установкой сверяется ещё раз; прежние версии удаляются при следующем скачивании.
- Установка — средствами системы:
  - deb, rpm, Arch: открыть папку с пакетом и показать команду установки (`sudo apt install ./…`, `sudo dnf install ./…`, `sudo pacman -U ./…`). Приложение не вызывает `sudo` и `pkexec`.
  - macOS: открыть `.dmg`; `.app` пользователь переносит сам.
  - Windows: запустить установщик NSIS и закрыть окно. Установщик ставит для текущего пользователя (ADR-027) и прав администратора не просит.
- Ошибки приходят во фронтенд кодом с параметрами, тексты — из словаря (ADR-008).

**Последствия.**
- У ai-memory появляется сетевой запрос, но только по явной кнопке и только к GitHub. Память агентов в сеть не уходит: запрос не несёт ничего, кроме заголовков HTTP.
- Подписи пакетов по-прежнему нет (ADR-027): сверка защищает от битой загрузки и подмены по дороге, но не от подмены в самом релизе.
- Имена вложений и формат `SHA256SUMS-*.txt` становятся контрактом между выпуском и приложением: меняются только вместе, с тестом.
- Индекс и бэкапы в каталоге данных обновление не трогает, как и раньше.
