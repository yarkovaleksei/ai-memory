# Архитектура

Стек и причины выбора — в [ADR-006](decisions.md#adr-006-стек-go--wails-v3-react-admin-yarn-4).

## Принципы

1. **Родные хранилища — источник правды.** Своей памяти у системы нет: индекс и кэш можно в любой момент удалить и пересобрать с диска.
2. **По умолчанию только чтение.** Запись включается явно и всегда идёт через предпросмотр diff.
3. **Ничего не теряем.** Перед каждой записью — снимок затрагиваемых файлов, после — коммит в собственный репозиторий бэкапов. Любую операцию можно откатить.
4. **Пишем так, как агент ожидает.** Claude — файлы фактов и индекс `MEMORY.md`; Codex — только ad-hoc-заметки (см. [storage-formats.md](storage-formats.md)).
5. **Локально.** Это десктоп-приложение без сетевого порта, данные никуда не уходят. Исключения — LLM-операции, которые явно вызывает пользователь, и они идут через установленные CLI агентов, и проверка обновлений по кнопке в настройках: она ходит только на GitHub за выпуском и пакетом ([ADR-031](decisions.md#adr-031-обновление-из-приложения-проверка-по-кнопке-сверка-и-установка-средствами-системы)).

## Каталоги ai-memory

Приложение поддерживает Linux, macOS и Windows ([ADR-009](decisions.md#adr-009-linux-macos-и-windows-с-самого-начала)), поэтому свои файлы кладёт по правилам каждой системы. Пути вычисляет `internal/config`, в остальном коде они не повторяются.

| | Linux | macOS | Windows |
|---|---|---|---|
| Настройки (`config.toml`) | `$XDG_CONFIG_HOME/ai-memory`, по умолчанию `~/.config/ai-memory` | `~/Library/Application Support/ai-memory` | `%AppData%\ai-memory` |
| Данные: индекс `index.db`, бэкапы `backups/` | `$XDG_DATA_HOME/ai-memory`, по умолчанию `~/.local/share/ai-memory` | `~/Library/Application Support/ai-memory` | `%LocalAppData%\ai-memory` |

Ниже «каталог данных» и «каталог настроек» означают эти пути.

## Модель данных

Типы живут в `internal/model`; ниже — суть, полные определения в коде.

```go
type Agent string // "claude" | "codex"

// Source — одно хранилище памяти: профиль Claude или поколение памяти Codex.
type Source struct {
    ID       string    // "claude:<корень>", "codex:v2", "codex:v1"
    Agent    Agent
    Label    string    // ".claude", "Codex v2"
    Root     string    // абсолютный путь корня памяти
    ReadOnly bool      // источник целиком только для чтения (Codex v1)
    Warnings []Warning // проблемы уровня источника (autoMemoryDirectory, ошибка чтения)
    Files    bool      // инструкции и навыки, а не память (ADR-019)
}

// Project объединяет память одного проекта из всех хранилищ (internal/catalog).
type Project struct {
    ID        string // "global", "path:<путь>", "encoded:<имя каталога Claude>"
    Path      string // пусто для глобальной памяти и нераспознанных
    Label     string
    Global, Temp, Resolved bool
    Agents    []Agent
    SourceIDs []string
    ItemCount int
}

type ItemKind string

const (
    KindClaudeFact     ItemKind = "claude-fact"           // файл факта Claude
    KindClaudeIndex    ItemKind = "claude-index"          // MEMORY.md
    KindCodexSection   ItemKind = "codex-summary-section" // раздел memory_summary.md (и MEMORY.md v1)
    KindCodexRollout   ItemKind = "codex-rollout"         // rollout_summaries/*.md
    KindCodexAdHocNote ItemKind = "codex-adhoc-note"      // extensions/ad_hoc/notes/*.md
    KindCodexRaw       ItemKind = "codex-raw"             // raw_memories.md (v1)

    // Фаза 4 (ADR-010, ADR-019): инструкции и навыки.
    KindInstructions ItemKind = "instructions" // CLAUDE.md, AGENTS.md и правила: файл целиком
    KindSkill        ItemKind = "skill"        // каталог с SKILL.md
)

// WriteMode показывает, что интерфейс может сделать с записью.
type WriteMode string

const (
    WriteDirect  WriteMode = "direct"   // факты Claude, ad-hoc-заметки
    WriteViaNote WriteMode = "via-note" // сгенерированное Codex: только через новую заметку
    WriteNone    WriteMode = "none"     // MEMORY.md (его ведёт writer) и всё из Codex v1
)

type Item struct {
    ID          string // sha256(источник + относительный путь + якорь)[:12]: стабилен между пересборками
    SourceID    string
    ProjectID   string
    Agent       Agent
    Kind        ItemKind
    Type        string // user | feedback | project | reference, если есть
    Title       string
    Description string
    Body        string         // Markdown без frontmatter
    Frontmatter map[string]any // разобранный frontmatter или заголовок rollout-сводки
    Links       []Link         // [[slug]], rollout_summaries/…, файлы из MEMORY.md; TargetID — ID цели, если нашлась
    File        string         // абсолютный путь
    Anchor      string         // заголовок раздела внутри файла
    ModTime     time.Time
    Hash        string // sha256 файла: оптимистичная блокировка при записи
    Write       WriteMode
    Warnings    []Warning // неожиданная структура, расхождение с индексом

    // Инструкции и навыки (ADR-019).
    Role   string // main | local | override | rule; навыки: user | project | system | synced | memory
    Target string // куда ведёт симлинк каталога навыка
    Shared bool   // на тот же каталог навыка указывают и другие записи
    Repo   string // корень git-репозитория проекта, где лежит файл
}

// Warning — код и параметры, а не текст: текст собирает фронтенд по словарю (ADR-008).
type Warning struct {
    Code   string            // например "claude.index.missing-file"
    Params map[string]string // например {"file": "pr-base-branches.md"}
}
```

`Frontmatter` в модели — только для показа. Writer фазы 2 перечитывает файл и правит frontmatter через `yaml.Node`, чтобы сохранить порядок ключей и неизвестные поля. Во фронтенд `Item` уходит как есть, в списке — без `Body` и со сниппетом совпадения.

## Адаптеры

У каждого адаптера одинаковый контракт (`internal/adapter`):

```go
type Adapter interface {
    Discover(ctx context.Context) ([]model.Source, error)             // найти корни
    Scan(ctx context.Context, src model.Source) ([]model.Item, error) // прочитать всё
    WatchDirs(src model.Source) []string                              // за какими каталогами следить
}
```

Планы записи (фаза 2) — функции пакетов адаптеров: `claude.PlanCreate`, `PlanUpdate`, `PlanUpdateRaw`, `PlanDelete`, `PlanFixIndex`; `codex.PlanNewNote`, `PlanForget`, `PlanUpdateNote`. Они только читают диск и возвращают `writer.Plan`; пишет `internal/writer`. Защита памяти Codex — `codex.Guard`, он подключается к writer'у как `writer.Guard`.

- **Claude.** Обходит профили, парсит frontmatter (терпимо к вариантам), восстанавливает путь проекта по `cwd` из jsonl, сверяет индекс `MEMORY.md` с файлами и записывает расхождения в `Warnings` (факт без строки в индексе, строка без файла).
- **Инструкции и навыки** (`internal/adapter/agentfiles`, ADR-019). Читает `CLAUDE.md` и правила профилей Claude, `AGENTS.md` и `AGENTS.override.md` в `CODEX_HOME`, навыки профилей, `CODEX_HOME/skills` и `~/.agents/skills`, а в каталогах проектов — их инструкции и навыки. Пути проектов ему проставляет библиотека по прочитанной памяти. Навыки с одним каталогом после раскрытия симлинков помечает общими и связывает ссылками. Навыки, выведенные Codex из памяти (`memories*/skills`), читает адаптер Codex — только чтение.
- **Codex.** Читает активное поколение — из настроек ai-memory, `[memories] version` в `config.toml` Codex или по самой свежей работе конвейера в его базах; неактивное — по настройке и только для чтения, режет `memory_summary.md` на разделы, читает заголовки `rollout_summaries`, перечисляет ad-hoc-заметки. SQLite Codex открывает только на чтение и только при необходимости (счётчики `usage_count`, `last_usage`).

`internal/library` связывает адаптеры, `catalog` и `index`: пересобирает индекс целиком при запуске и после изменений файлов (пауза 400 мс после последнего события `fsnotify`), набор наблюдаемых каталогов обновляет после каждой пересборки. Порядок пересборки: сначала память, затем инструкции и навыки — по путям проектов из памяти и из каталогов проектов Claude без памяти ([ADR-025](decisions.md#adr-025-пути-проектов-для-инструкций--и-из-каталогов-проектов-claude-без-памяти)). В корне профиля Claude, `CODEX_HOME` и каталогах проектов наблюдение реагирует только на имена файлов инструкций (`adapter.NameFilter`): историю, логи и сессии агенты пишут туда постоянно.

## Запись

Операции: `create`, `update`, `delete`, `move` (перенос в другой проект или агент), `merge` (несколько записей → одна).

Каждая операция проходит один и тот же путь:

1. **План.** Адаптер превращает операцию в список файлов с содержимым до и после (`writer.Plan`). Для Claude: файл факта и строка в `MEMORY.md`. Для Codex: новая или изменённая ad-hoc-заметка в активном поколении.
2. **Предпросмотр.** Интерфейс показывает unified diff по каждому файлу. Без подтверждения ничего не пишется.
3. **Проверки перед записью:**
   - `Hash` каждого файла совпадает с тем, что видел пользователь, иначе конфликт и повторный план;
   - для Codex консолидация не идёт: ai-memory берёт её файловый lock на время записи и проверяет задачу в `jobs` ([ADR-012](decisions.md#adr-012-бэкапы-через-системный-git-блокировка-codex-через-его-же-lock-файл)); под `CODEX_HOME` меняются только заметки, и они не удаляются;
   - путь лежит внутри разрешённых корней (защита от `..` и симлинков). Исключение — цель симлинка навыка: она добавляется в разрешённые корни явно, и план показывает, что изменение затронет всех, кто ссылается на этот навык ([ADR-010](decisions.md#adr-010-инструкции-и-навыки-агентов--тоже-в-охвате));
   - для проектных инструкций — предупреждение, что файл лежит в git-репозитории проекта.
4. **Снимок** текущего содержимого в репозиторий бэкапов (`backups/` в каталоге данных, отдельный git).
5. **Атомарная запись:** временный файл в том же каталоге и `os.Rename`. На Windows замена не удаётся, пока файл открыт другим процессом: writer распознаёт эту ошибку и повторяет попытку с паузой, а после нескольких неудач возвращает конфликт.
6. **Коммит** в репозиторий бэкапов с описанием операции. Откат — обратное применение коммита, тоже через план и diff.

Запрещено всегда: писать в сгенерированные файлы Codex, удалять ad-hoc-заметки, трогать что-либо вне каталогов памяти и разрешённых корней инструкций и навыков (каталоги проектов, `~/.agents`, цели симлинков навыков — [ADR-020](decisions.md#adr-020-как-пишутся-инструкции-и-навыки)).

Навык ставится в другого агента копией каталога или симлинком на него. Симлинки writer создаёт и удаляет сам, но никогда не пишет через них; откат знает, где был симлинк ([ADR-023](decisions.md#adr-023-навык-ставится-в-другого-агента-копией-или-симлинком-через-writer)).

У плана бывают предупреждения: файл в git-репозитории проекта, общий навык. Второе нужно подтвердить отдельно, иначе «Записать» неактивна.

Правило переносится между файлами инструкций разделом по заголовку: вставкой в другой файл проекта и, при переносе, удалением из исходного одной операцией. Отсутствующий `AGENTS.md` или `CLAUDE.md` при этом создаётся, и только откат этой операции может его удалить. План предупреждает об импортах `@путь`, которых Codex не понимает, и о затенённом или условном целевом файле ([ADR-021](decisions.md#adr-021-перенос-правила--раздел-по-заголовку-вставкой-в-другой-файл-инструкций)). Для проекта, где правила агентов живут порознь, предлагается приём «`AGENTS.md` — основной»: выбранные блоки `CLAUDE.md` уходят в `AGENTS.md`, а в `CLAUDE.md` остаётся импорт `@AGENTS.md` ([ADR-022](decisions.md#adr-022-приём-agentsmd--основной--блоки-claudemd-переносятся-в-claudemd-остаётся-импорт)).

## Индекс и поиск

- SQLite в `index.db` в каталоге данных, таблица записей и FTS5 по заголовку, описанию и телу.
- Пересборка с нуля при запуске и после событий `fsnotify` (одной транзакцией: читатель видит старое или новое состояние). После пересборки сервис шлёт событие Wails `index:updated`, и интерфейс перечитывает данные.
- Сортировка по названию — по отдельной колонке `sort_title` (нижний регистр, «ё» как «е»): `NOCASE` в SQLite понимает только латиницу.
- Записи временных проектов в общий список и поиск не попадают, пока не включён фильтр «Показать временные» или не выбран сам временный проект.
- Стандартный токенизатор не знает русских словоформ, поэтому в фазе 1 поиск идёт по префиксам (`ветк*`); стемминг — позже, если понадобится.
- `remove_diacritics` в FTS5 работает только для латиницы: «ё» и «е» для него разные буквы. Индекс сам приводит «ё» к «е» и в индексируемом тексте, и в запросе. Проверено тестом `internal/index/fts5_test.go` на `modernc.org/sqlite`.
- Дубли и противоречия ([фаза 3](phases/03-cross-agent.md)): ai-memory их не угадывает — пользователь отмечает записи в списке, а модель по запросу даёт черновик объединения или ищет противоречия среди отмеченных ([ADR-018](decisions.md#adr-018-без-поиска-похожих-по-совпадению-слов-объединение-и-противоречия--для-отмеченных-в-списке)). Файлы инструкций тоже отмечаются, но только для проверки: модель ищет противоречия и факты памяти, которые повторяют правила инструкций ([ADR-024](decisions.md#adr-024-инструкции-отмечаются-в-списке-только-для-проверки-противоречий-и-дублей-с-памятью)).

## LLM-операции

Только по явному действию пользователя: «объединить», «найти противоречия», «переформулировать для другого агента». Вызов через установленные CLI в неинтерактивном режиме (`claude -p`, `codex exec`) через `os/exec`, без API-ключей ([ADR-005](decisions.md#adr-005-llm-операции-через-cli-агентов)). Результат LLM — всегда черновик, который проходит обычный путь записи с diff.

Как именно вызываются CLI, чтобы не создавать память и не тратить лишнего, — [ADR-015](decisions.md#adr-015-llm-черновики-один-запрос-из-постоянного-каталога-кандидатов-отбирает-tf-idf): постоянный рабочий каталог `<каталог данных>/llm`, ответ по JSON-схеме, модели уходят только отмеченные пользователем записи.

## Безопасность

- В собранном приложении сетевого порта нет: интерфейс вызывает Go напрямую через привязки Wails.
- В режиме разработки (`wails3 dev`) фронтенд раздаёт dev-сервер Vite на `127.0.0.1:9245`. Проверено 2026-11-10 на Linux: процесс приложения не слушает ни одного TCP-порта, а страница, открытая в обычном браузере с адреса Vite, получает 404 на `POST /wails/runtime` — вызвать Go-сервисы снаружи окна нельзя, видна только вёрстка. Кроме того, `wails3 task dev` по умолчанию работает на фикстурах.
- Ядро принимает от интерфейса только идентификаторы записей и планов, а не произвольные пути. Каждый путь перед чтением и записью проверяется на принадлежность разрешённым корням.
